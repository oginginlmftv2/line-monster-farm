# 技DB・血統ページ設計

作成: 2026-09-03
対象タスク: S1
本番影響: ⚪（技DBを空でコミットするため、公開HTML・sitemapは変化しない）

## 1. 目的と範囲

モンスターの技を構造化データとして持ち、血統ページで一覧表示する基盤を置く。
S1では技データを0件で始めるため、既存ページへの導線も表示も変わらない。
GAS・シート・Workflowも変更しない。

本番入力は次の空DBで開始する。

```json
{ "schemaVersion": 1, "generatedFrom": ["手入力"], "generatedAt": null,
  "counts": { "skills": 0, "bloods": 0 }, "skills": [] }
```

空DBでは血統ページを1枚も生成せず、`sitemap.xml` も変えない。

## 2. なぜ血統ページなのか

技は血統ごとに共通で、間合い（零・近・中・遠）× ランク（1〜6）のマトリクスを成す。
モンスター詳細ページ全356件に同じ表を出すと完全な重複コンテンツになるため、
**血統単位が重複を起こさない唯一の置き場所**である。

血統ページは 2026-08-18 に「作らない」と決定していたが、その根拠は
「導入文が34血統×約8,800字必要」の一点だった。主コンテンツが事実データの技表に変わり、
導入文なしで可視800字を超えるため、前提が成立しない。`docs/build-spec.md` 3-2 を差し替えた。

モンスター詳細ページには固有技と解放技だけを載せ、血統共通技の全量は載せない（S2）。

## 3. DB

### `src/data/monster-skills.json`

主キーは `skillId`（`sk-####`）。公開URLの実体ではなく、血統ページ内のアンカーとして使う。

| フィールド | 値 |
|---|---|
| `skillId` | `sk-####`。**バージョングループ共通**で、版が上がっても変わらない |
| `name` | 技名 |
| `version` | 1以上の整数。`blood` + `name` が同じものは同じ技の別の版 |
| `blood` | `monster-ids.json` の `bloodOrder` にある血統名（34値） |
| `range` | 技を発動できる間合い。`遠` `中` `近` `零` |
| `rank` | 1〜6の整数 |
| `moveTo` | 発動後に移動する先。移動しない技は `null`（多数派） |
| `aura` | `赤` `青` `黄` `黒` `白` `緑` `無` の7値 |
| `skillType` | 技種（`ちから` `かしこさ` など） |
| `guts` | 消費ガッツ（0以上の整数） |
| `damage` / `accuracy` / `gutsDown` / `critical` | `SS`〜`G` の評価または `null`。4項目とも `SS` を取りうる |
| `abilities` | `{ abilityId, unlock }` の配列。`unlock` は `{ monsterId, level }` または `null` |
| `icon` | 技アイコンのファイル名。S1では未使用で常に `null` |
| `unique` | 固有技なら `true` |
| `owners` | 固有技を使えるモンスターの4桁ID配列。共通技では空配列 |
| `unlockedBy` | 技登録の解放元。`{ monsterId, rarity }` の配列。`rarity` は★1〜10 |
| `note` / `sortOrder` / `status` | 補足・表示順・状態 |

ゲーム内グリッドの列は「技を発動できる間合い」である。移動先を持つ技の `A→B` の A は
発動間合いと必ず一致するため、DBは B（`moveTo`）だけを持ち、A は `range` から復元する。

`unique` と `owners` を分けるのは、固有技に「複数体が使える」パターンがあるため。
`unlockedBy` は別概念で、「どのモンスターを★いくつまで上げると技登録できるようになるか」を持つ。
レアリティが必要なので単なるID配列ではなく `{ monsterId, rarity }` の組にする。
血統共通技は登録さえすれば所属モンスター全員が使えるため、`owners` は空のままでよい。

### `src/data/skill-abilities.json`

技能力は既存の `src/data/assist-abilities.json` とは**別DB**にする。既存DBは `cardId` を
必須とするアシストカード専用で、技を混ぜると `linkStatus` / `rarity` / `source` の意味が壊れる。
外形（`schemaVersion` / `generatedFrom` / `counts` / 本体配列）は既存に合わせる。

| フィールド | 値 |
|---|---|
| `abilityId` | `sab-####`。**バージョングループ共通**で、版が上がっても変わらない |
| `name` | 表示名（`狩の印Lv2`）。同名は同じ技能力の別の版 |
| `version` | 1以上の整数 |
| `baseName` / `level` | Lvを分解した値（`狩の印` / `2`）。Lvが無い能力は `name` と同じ・`null` |
| `description` | 効果テキスト。改行は `\n`。HTMLタグは持たない |
| `buffs` | バフ・デバフID（`bf-####`）の配列。**取り込みが自動で入れる導出値**で、手入力しない |
| `tags` / `sortOrder` / `status` | 分類・表示順・状態 |

`description` に生のHTMLを入れないのは、`assist-abilities.json` が `<br>` を含む形式で、
出力時のエスケープ判断が読み手に伝わらないため。改行は `\n` で持ち、描画時に `<br>` へ変換する。

### `src/data/skill-buffs.json`

`[霊魂]` `[火傷Lv1＜20秒＞]` のように技能力テキストへ現れる、ゲーム内ヘルプ定義の共通状態。
技能力の説明だけでは意味が読み取れないため、定義を別DBに持ってページで補う。

| フィールド | 値 |
|---|---|
| `buffId` | `bf-####` |
| `name` | `霊魂` `火傷` など。DB内で一意 |
| `kind` | `バフ` か `デバフ` |
| `description` | ヘルプ本文。改行は `\n` |
| `note` | ヘルプの `※` 行（`最大Lv9まで累積` など）。無ければ空文字 |

入力元は血統をまたぐので `src/data/_source/buffs.tsv` の1枚だけ。技能力側の `buffs` は
取り込みが `detectBuffs()` で自動判定する。判定は**テキストの完全一致だけ**で、
(1) `description` の角括弧の中身から `Lv\d+` と `＜…＞` を外したもの、
(2) `name` から接頭辞（`祝：` `疫：`）と末尾の `Lv\d+` を外したもの、の2経路。

素の部分一致を取らないのは、`混乱` `衰弱` のような一般語や、`[終盤]` `[有利]` のような
発動条件と誤爆するため。角括弧にあってバフDBにも `NON_BUFF_TOKENS` にも無いものは
**未登録候補として取り込みが報告する**ので、その場で判断して足す。

### バージョン：技も技能力も上書きしない

ゲーム側のアップデートで内容が変わる。上書きするとロールバックできないので、
**同名は新しい版として積み、表示は最新版だけ**にする。

| | グループのキー | 固定ID |
|---|---|---|
| 技 | `blood` + `name` | `skillId` |
| 技能力 | `name` | `abilityId` |

**IDをグループ共通で固定する**のが要点。`skillId` は血統ページ内のアンカーで、
モンスター詳細からの `index.html#<skillId>` リンクと `verify.js` の突き合わせが依存している。
`abilityId` は技側（`skill.abilities[].abilityId`）からの参照キーなので、固定なら
技のデータを触らずに技能力だけ差し替えられる。DBの一意キーは `ID + version`。

旧版はDBに残るが、`selectCurrentVersions()` を通した結果だけが描画される。
共通枠（`blood`×`range`×`rank` に共通技1件）の検査も最新版だけを対象にする。
旧版は必ず同じ枠に居るため、全件で見ると必ず衝突するからである。

`version` は取り込みがTSVの出現順で振るので、入力者は**新しい行を末尾に足すだけ**でよい。
転記ミスの訂正は版を足さずその行を直す。両者を取り違えないよう、
隣り合う版で内容が完全に同じならエラーで止める。

### 技能力の解放条件をどこに持つか

同じ名前の技能力が複数の技に付く（`テクニックレイズ` など、高ランク技に多い）。
**同名は同一の能力として扱い、辞書は1件（＝1バージョングループ）にする。**
レベル差はゲーム側が名前で分けているため（`祝：霊魂Lv2` と `祝：霊魂Lv8`、
`テクニックレイズ` と `テクニックオーバー`）、「名前 → 効果テキスト」は関数として扱える。
同名で内容が変わったときは、別レコードではなく**同じ `abilityId` の次の版**にする。

一方で**解放条件は技ごとに違う**ため、能力の属性ではなく「技×能力」の線に持たせる。

```json
"abilities": [
  { "abilityId": "sab-0004", "unlock": null },
  { "abilityId": "sab-0005", "unlock": { "monsterId": "2629", "level": 10 } }
]
```

名前で辞書を引く方式を保てるので、シート側の参照が壊れない。
別レコードに分けると `テクニックレイズ@八嵐天衝` のような複合キーが必要になり、転記の負担が増える。

`level` は技登録の `unlockedBy.rarity` と**同じ1〜10の尺度**。
画面では白星が1〜5、ピンク星が6〜10（ピンクの数＋5）で表示される。

## 4. 検証

DB検査の正は `build.js` の `validateSkillData(skillDb, abilityDb, idsJson)` とする。
通常ビルド、`scripts/verify.js` セクション19、`scripts/test-skill-build.js` が同じ関数を使い、
ID・血統・間合い・ランク・オーラ・評価・参照先・固有技の整合を重複実装しない。

主な検査:

- `skillId` / `abilityId` は書式が正しく、**同じID内で `version` が重複しない**こと
- 技は `blood`+`name`、技能力は `name` とIDが1対1であること（グループが割れていないこと）
- `version` が各グループで1からの連番で、隣り合う版の内容が同じでないこと
- `buffId` の書式・一意性、バフ名の一意性、`kind` が `バフ`/`デバフ` であること
- 技能力の `buffs[]` が実在の `buffId` を指し、重複しないこと
- `blood` が `bloodOrder` にある / `range` 4値 / `rank` 1〜6 / `aura` 7値
- 評価は `/^(?:SS|[SABCDEFG])\+?$/`。**各段に `+` 付きが存在する**。
  最上位は `SS` で、**ダメージ・命中率・ガッツダウン・クリティカル率の4項目すべてに存在する**
  （初出はキュービ種 王狐炎衝、2件目がイルミネ種 王武天覇のクリティカル率）
- `moveTo` が `range` と同じ値でないこと（移動しない技は `null`）
- `abilities[]` の `abilityId` が `skill-abilities.json` に実在し、同じ技に重複しないこと
- `abilities[].unlock` が `null` か、実在モンスター＋★1〜10であること
- 同じ `name` の技能力で `description` が食い違わないこと
- `owners[]` のモンスターIDが実在し、技と同じ血統であること
- `unlockedBy[]` が `{ monsterId, rarity }` の組で、IDが実在し `rarity` が★1〜10の整数であること
- `unique: true` なら `owners` 1件以上、`unique: false` なら `owners` は空
- 同一 `blood` × `range` × `rank` に共通技が2件以上ないこと（固有技は例外／**最新版のみ対象**）

`scripts/verify.js` セクション19は加えて、技データの有無と生成された血統ページの一致、
技表の行列の骨格、技チップ数と詳細行数の一致、`noscript` と `blood.css` の存在を検査する。

## 5. 生成ページ

構成は `docs/build-spec.md` 5-9 が正。要点だけ再掲する。

- 行＝ランク1〜6、列＝発動間合い（遠・中・近・零）。1セルは技チップの縦積みリスト
- **色は1つの意味だけを担わせる**（詳細は `docs/build-spec.md` 5-9）。
  列見出し＝間合い、チップと詳細（見出し列・背景・左の色帯）＝技種、ドット＝オーラ。
  表のセルは白、開いた詳細だけ技種の色で塗って境界を作る
- 移動先は表に出さず詳細だけで扱う。未実装の枠は空セル
- 技詳細は該当ランク行の直下へ開く行内アコーディオン。右上に閉じるボタン。
  アンカー遷移とモーダルは使わない
- **バフ・デバフは、それを起こす技能力のカードの中**に出す。見出しは付けない。
  技単位でまとめるとどの能力が付けるものか分からなくなる
- **技能力の見出しは技能力が0件でも出す。**その下に「なし」と書く。
  見出しごと消すと技によって構造が変わり、読み手が「未入力」と区別できない
- 連動能力は表示しない（ゲーム内に項目はあるが、ページでは扱わない）
- 技アイコンはS1では使わない。`icon` フィールドだけ用意し、チップを
  「アイコン＋名前の横並び」にすれば縦積みは崩れないので、構造は先に確定させている

## 8. S2: モンスター詳細への反映と導線

構成は `docs/build-spec.md` 5-10 が正。

- モンスター詳細に「固有技」「〈名前〉のレア度上昇で解放できる技」「〈血統〉種の技」の3セクション。
  **血統共通技の全量は出さない**（血統ページと重複するため）。該当0件ならセクションごと出さない
- リンクは `index.html#<skillId>`。血統ページは詳細ページと同じディレクトリにある
- 血統ページはハッシュを見て該当技を開く
- パンくずと JSON-LD に血統を1段挟む（血統ページがある場合だけ）
- モン類ページの血統見出しを血統ページへのリンクにし、技の件数を添える

`scripts/verify.js` セクション19が、掲載された技が固有技または解放技であることを
モンスター詳細ページ全件に対して突き合わせる（血統共通技の混入を機械的に防ぐ）。
