# 本番影響とマージ方針

**作業を開始する前に、その作業が本番に影響するかを必ず確認すること。**
進捗管理チャットは、プロンプトを渡すときに本番影響の区分を必ず明記する。

## 区分

| 記号 | 意味 | 判断 |
|---|---|---|
| 🔴 | **公開サイトが変わる** | マージ＝公開。実行タイミングを所有者が決める |
| 🟡 | **本番データが変わる**（Firestore・シート） | 表示は変わらないが、失敗すると復旧が必要 |
| ⚪ | **影響なし** | リポジトリ内で完結。いつマージしてもよい |

## 現在のデプロイ構成（重要）

**現在、GitHub Pages は `main` から直接配信している。**
したがって **`main` へのマージ＝即座に本番公開** である。ステージングは存在しない。

P5-4 でデプロイを `gh-pages` に移し、**ビルドを手動トリガー（`workflow_dispatch`）にする。**
これにより「マージ」と「公開」が分離され、公開は明示的な操作になる。

```
現在   main にマージ ──────────────► 即公開
P5-4後 main にマージ → （手動実行）─► ビルド → gh-pages → 公開
```

**P5-4 は、この計画で最も慎重に扱うタスク。** 配信元の切り替えを誤るとサイトが落ちる。
切り替え直後は必ずトップページと主要記事5本を目視確認すること。

## マージ方針

**「全作業の完了後にまとめてマージ」はしない。** 理由は3つ。

1. **P3（クリーンアップ）は時間がかかる施策**。薄いページをsitemapから外しても、
   Search Console に反映されるまで数週間かかる。遅らせるとP9（再申請）がそのぶん遅れる
2. 巨大な1回のマージは、問題が起きたとき原因の切り分けが不可能になる
3. ⚪区分のタスクは本番に何の影響もないので、留め置く理由がない

### 段階的なマージ順

| 段階 | 対象 | 区分 | タイミング |
|---|---|---|---|
| 1 | P1（ルール・ID）、P2（データ移行） | ⚪ | 完了次第すぐ。本番出力は1文字も変わらない |
| 2 | P3（クリーンアップ） | 🔴 | **早いほどよい。** 単独で公開して反映を待つ |
| 3 | P4-2（画像配置） | ⚪ | 参照されるまで無害 |
| 4 | P5（ビルド基盤） | 🔴 | P5-4のみ要注意。切替後に目視確認 |
| 5 | P6（ページ生成） | 🔴 | 本命。公開後 Search Console を監視 |
| 6 | P7（カード記事） | 🔴 | 随時 |
| 7 | P8（CMS） | 🔴 | P8-1 で管理画面のURLが変わる |

**段階2（P3）を段階5（P6）まで待たないこと。** ここが最も重要な判断。

## Firestore のセキュリティルール（P0-1）

### 確認の手順（読むだけ。本番に影響しない）

```
1. https://console.firebase.google.com/ を開く
2. プロジェクト line-monster-farm を選ぶ
3. 左メニュー「Firestore Database」→ 上部タブ「ルール」
4. 表示されているルールのテキストを確認する
```

`allow read, write: if true;` のようになっていれば、**誰でも書き換え・削除できる状態**。

### ★ルールを変更する前に必ず知っておくこと

**このサイトは、公開ページが認証なしでFirestoreを読んでいる。**
読み取りを禁止すると、**公開中のページが即座に壊れる。**

公開ページが読んでいるコレクション:

| コレクション | 読んでいるページ | 止まると起きること |
|---|---|---|
| `monsters/{id}` | `monsters/monster.html` | 解説・編成が消える |
| `monsters/{id}/comments` | 同上 | コメントが消える |
| `cards/{id}` | `cards/card.html` `assist.html` | 評価・編成・解説が消える |
| `cards/{id}/comments` | `cards/card.html` | コメントが消える |
| `cardAbilities/assignments` | `cards/card.html` | 能力画像が出なくなる |
| **`monsterImages/assignments`** | **`monsters.html`（公開一覧）** | **一覧の画像が出なくなる** |

**`allow read: if false` にしてはいけない。**

### 推奨するルール

```
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {

    // 読み取りは全面許可（現状維持。これを閉じるとサイトが壊れる）
    // 書き込みは全面禁止（65,658字の解説を守る）
    match /{document=**} {
      allow read: if true;
      allow write: if false;
    }
  }
}
```

**影響**: 公開ページの表示は一切変わらない。書き込みだけが止まる。

**副作用として止まるもの:**

| 機能 | 対処 |
|---|---|
| `monster.html` `card.html` からの解説編集 | P2でJSONへ移行するので問題ない。それまでは編集しない |
| 訪問者のコメント投稿 | 投稿できなくなる。必要なら下の緩和ルールを使う |
| **`monster-match.html` の画像割り当て保存** | **P4-1で必要。** 下の「作業窓」を使う |
| `ability-match.html` `assist-effect-input.html` | 同上 |

### コメント投稿だけ残したい場合

Firestoreのルールは「いずれかが許可すれば通る」ので、上のルールに追記する。

```
    match /monsters/{id}/comments/{c} {
      allow read: if true;
      allow create: if true;
      allow update, delete: if false;
    }
    match /cards/{id}/comments/{c} {
      allow read: if true;
      allow create: if true;
      allow update, delete: if false;
    }
```

ただし**無認証の書き込み口を残すことになる**（スパム投稿が可能）。
コメント機能の利用実績が無いなら、残さないほうが安全。

### 管理作業のための「作業窓」

P4-1（画像マッチング）など、管理ツールでFirestoreに書く必要があるときは、
**作業する時間だけルールを開け、終わったら必ず閉じる。**

```
1. PROGRESS.md の備考に「YYYY-MM-DD HH:MM ルールを開放」と記録する
2. 該当コレクションだけ allow write: if true; に変更して公開
3. 作業する
4. allow write: if false; に戻して公開
5. PROGRESS.md に「HH:MM 閉鎖」と記録する
```

**開けたまま放置しないこと。** 記録を残すのは、閉め忘れを検出するため。

### ★P4-1 の前に確認すべきこと

`monsterImages/assignments` に、**過去のマッチング結果が既に保存されている可能性がある。**
`monster-match.html` の保存先がここで、`monsters.html` がそれを読んでいる。

P4-1に着手する前に、このドキュメントの中身を確認すること。
既に大半が割り当て済みなら、**93体のマッチング作業はほとんど不要**かもしれない。

確認方法: Firebaseコンソール → Firestore Database → `monsterImages` → `assignments`
