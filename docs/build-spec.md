## 0. 目的と絶対条件

`monster-ids.json`に存在する全モンスターの詳細を静的HTMLとして出力し、
生成HTMLの可視文字数が800字以上のページだけをインデックス対象にする。

### 絶対条件（違反したらビルドを失敗させる）

1. **ゲート条件を満たさない詳細ページは noindex,follow にする。**
   noindex ページは sitemap に載せず、AdSense スクリプトも出力しない。
2. **既存の公開HTMLを上書きしない。** 生成先は本仕様で定めたパスのみ。
3. **出力は決定的であること。** 同じ入力なら常に同じバイト列を出力する。
   出力に現在時刻・乱数・実行順依存の要素を含めない。差分が毎回汚れるため。

## 2. 出力

### 2-1. 生成するパス

```
monsters/<monSlug>/index.html                      モン類ページ    6件
monsters/<monSlug>/<bloodSlug>/<id>.html           詳細ページ    入力全件
sitemap.xml                                        再生成
                                                   ─────────
                                                   HTMLは入力件数 + 6ページ
```

**血統ページ（`monsters/<monSlug>/<bloodSlug>/index.html`）は生成しない。**
理由は 3-2 を参照。血統ディレクトリはパスとして存在するが、`index.html` は置かない。

例: `monsters/mazoku/pixie/0101.html`

### 2-2. ★`monsters/index.html` は生成しない

一覧ページは既存の `monsters.html`（ルート直下）が担う。これは保護対象の公開URLで、
インデックス済みの可能性がある。`monsters/index.html` を作ると**重複コンテンツになる**ため作らない。

階層の入口は `monsters.html` から6つのモン類ページへリンクする形にする（P6-4で対応）。

### 2-3. 既存ファイルとの共存

`monsters/monster.html`（旧詳細ページ）は `noindex,nofollow` のまま残し、
旧 `?id=<arrayIndex>` から新URLへ転送する。削除せず、生成物と同じディレクトリに同居する。

### 2-4. 生成物の扱い

**生成したHTMLはリポジトリにコミットする。**
現在 GitHub Pages は `main` から配信しているため、コミットしないと公開されない。
各生成ファイルの先頭に、次のHTMLコメントを入れること。

```html
<!-- このファイルは build.js が自動生成しています。直接編集しないでください。 -->
<!-- 元データ: src/data/monsters-editorial.json / src/data/monster-ids.json -->
```

## 3. ゲート条件

### 3-1. 詳細ページ（入力全件）

`monster-ids.json`にある全件のページを生成する。ゲートは**インデックスするかどうか**を決める。

```
visibleChars(生成したHTML) >= 800  → インデックス対象（2026-08-22: 52件）
未満                                → noindex,follow（2026-08-22: 299件）
```

**ソース字数ではなく、レンダリング後の可視文字数を実測して判定する。**
以前は「解説＋編成のソース500字以上」で代用していたが、UIを変更すると
可視文字数がずれ、基準を割るページがインデックスされる事故が起きたため、
実測方式に変更した（2026-08-19）。今後デザインを変えても自動で追従する。

判定は「本文を組み立てる → 測る → head を組み立てる」の順で行う。
robots メタと AdSense スクリプトは head にあり可視文字数に影響しないため、循環しない。

noindex のページは sitemap に載せず、**AdSenseスクリプトも出力しない**。
解説を書き足して800字を超えれば、次回のビルドで自動的にインデックス対象へ昇格する。

この制御は `scripts/verify.js` のセクション9が機械的に検査する。

### 3-2. ★血統ページは生成しない（2026-08-18 決定）

`monsters/<monSlug>/<bloodSlug>/index.html` を**作らない。**

**理由**

血統ページには、その血統についての導入文が必要になる。34血統ぶんで約8,800字。
このサイトの唯一の差別化資産は「現役トップランカーが書いている」ことであり、
改善計画は一貫して「AI感の除去」を掲げてきた。
**運営者以外が書いた8,800字を入れることは、その方針と正面から矛盾する。**

とくに詳細ページが0件の8血統（アローヘッド・グジラ・ニャー・ヒノトリ・
スエゾー・ゲル・プラント・ワーム）は、運営者の解説が1本も存在しないため、
書こうとすればゲーム知識の捏造になる。

**代わりにモン類ページが血統ハブの役割を兼ねる**（5-3 を参照）。
血統単位のナビゲーションはモン類ページ内のグループ表示で提供するため、失われない。

**構造上の問題は生じない。** 血統ディレクトリは詳細ページの置き場として存在し、
その下にぶら下がる別のページは無いため、階層が途中で切れることもない。

**将来の追加**

血統ページを後から追加する場合は、本節を書き換えて 5 章に構成を定義すること。
その際の必要導入文字数は次式で算出する（詳細ページが増えるほど必要字数は下がる）。

```
必要字数 = max(150, ceil50( 850 - (所属数×20 + 詳細ページ数×100 + 300) ))
```

### 3-3. モン類ページ（6件）

```
生成する条件:
  taxonomy.json の monTypes.<monSlug> に
    - sections が3つある（おすすめ血統 / 師匠カードの有無 / 実装済みのモン類MRと特徴）
    - 各 section の items が1件以上ある
    - 全 items の subheading + body の合計が400字以上
```

本文は**運営者本人が執筆する**（P6-2）。`src/data/taxonomy.json` に格納する。
ビルド側でテキストを整形・要約・生成しないこと。**そのまま出力する。**

条件を満たさないモン類はページを生成せず、理由を明示してログに出すこと
（例: `無機: 合計320字。400字必要。80字不足` / `創造: sections が2件。3件必要`）。

**揃った分だけ生成する。** 6本すべてが揃うまで待つ必要はない。

#### taxonomy.json の構造

```json
{
  "monTypes": {
    "kemono": {
      "name": "獣族",
      "sections": [
        {
          "heading": "おすすめ血統",
          "items": [
            { "subheading": "キュービ種", "body": "自身に完全回避を…" }
          ]
        }
      ]
    }
  }
}
```

- キーは `generate-ids.js` の `MON_SLUG` の値（`souzou` `genrei` `mazoku` `kemono` `kaibutsu` `muki`）
- `subheading` は `null` を取りうる（「実装なし。…」のように小見出しが無い項目）。
  `null` の場合は小見出しを出力せず、本文だけを出す
- **`sections` と `items` の配列順が出力順**。ビルド側で並べ替えないこと
- 現時点の字数: 創造592 / 幻霊604 / 魔族569 / 獣族869 / 怪物517 / 無機664
- **見出し文言は `taxonomy.json` の `heading` が正**。変更したい場合はJSONを直すだけでよく、`build.js` の修正は不要

### 3-4. ゲートで落ちた場合の扱い

**リンク切れを作らないこと。** 全モンスターに詳細ページがあるため、
モン類ページのカードはすべて詳細ページへのリンクを持つ。

- **血統は常にリンクなしのテキストとして表示する**（血統ページを作らないため）
- パンくずの親が存在しない場合は、その階層をパンくずから省く
  詳細ページのパンくずは、モン類ページがあれば
  `トップ > モンスター一覧 > <モン類> > <名前>` となる（血統は入れない）

## 4. データの解決ルール

### 4-1. 画像の解決順（既存コードと同一にすること）

```
1. monsters-data.js の localImg があればそれ           → monster/<localImg>
2. monster-images.json に該当IDがあればそれ            → monster/<filename>
3. どちらも無ければ GameWith のURL
   https://img.gamewith.jp/article_tools/monsterfarm-line/gacha/Lmonfar_monster_<gwImg>.png
4. gwImg も無ければ画像なし（<img> を出力しない）
```

この順序は `monsters.html` の既存実装と同じ。変更しないこと。

**2026-08-22時点のインデックス対象52体は、全件が 1 または 2 で解決する**ことを確認済み。
3 に落ちた場合はログに警告を出すこと（想定外のため）。

### 4-2. 編成データの表示

`formations` は次の構造。

```json
[{ "title": "おすすめ編成①", "cards": ["a10j-MR-fureria", ...5枚], "rental": "a24j-MR-vitoniru" }]
```

- カードIDは `cards/cards-data.js` の `cardsData[id].name` で**カード名に変換**して表示する
- `cards` は5枚、`rental` は1枚（レンタル枠として区別して表示）
- `cardsData` に存在しないIDは、**カードIDをそのまま表示し、ログに警告**を出す
- カード画像は表示しない（詳細ページの主役は解説のため）

### 4-3. 解説の整形

`explanation` は改行を含むプレーンテキスト。多くが `・` または `･` で始まる箇条書き。

- 改行で分割し、行頭が `・` または `･` の行が**2行以上連続する場合は `<ul><li>` に変換**する
- それ以外の行は `<p>` にする
- 空行は段落の区切りとして扱う
- **HTMLエスケープを必ず行うこと**（`< > &` を実体参照に）
- 行頭の `・` `･` は `<li>` に変換した際に取り除く
- 全角スペースによるインデント（`　`）は保持する

## 5. ページ構成

### モン類の表示順（公式順・確定）

    創造 → 幻霊 → 魔族 → 獣族 → 怪物 → 無機
    souzou → genrei → mazoku → kemono → kaibutsu → muki

ゲーム公式の並びに合わせた（2026-08-19 確定）。
実装上の正は `build.js` の `MON_ORDER`。表示順が関わる箇所はすべてこれを使う。
`monster-ids.json` の出現順や `taxonomy.json` のキー順に依存しないこと。

手書きページ（`index.html` / `monsters.html`）のモン類の並びも、この順に揃える。

**血統の順序（`BLOOD_ORDER` 34件）はモンスターIDの根拠であり、絶対に並べ替えない。**
今回統一したのはモン類の表示順のみ。

### 5-1. 共通要素（全生成ページ）

既存ページと同じヘッダー・ナビ・フッターを使う。`style.css` のクラスのみ使用。

| 要素 | 内容 |
|---|---|
| `<title>` | ページ種別ごとに後述。**全ページでユニーク** |
| `<meta name="description">` | インデックス対象は**全ページでユニーク**、40〜140字 |
| `<link rel="canonical">` | 自己参照の絶対URL |
| パンくず | 後述 |
| AdSenseタグ | インデックス対象にのみ、既存ページと同じものを入れる |

インデックス対象には `<meta name="robots">` を入れず、noindex 対象には
`<meta name="robots" content="noindex,follow">` を入れる。

### 5-2. 詳細ページ

```
パンくず: トップ > モンスター一覧 > <モン類> > <名前>
          （血統ページを作らないため、血統は入れない。3-4 を参照）

h1: <名前>

基本情報（.detail-card を使う）
  画像
  モン類 / 主血統 / 副血統 / オーラ / 限定ラベル（あれば）
  モン類・血統はリンクなしのテキスト

評価解説   ← 本文の主役
  explanation を 4-3 のルールで整形して出力
  explanation が無い場合はセクション自体を出力しない

おすすめ編成（formations がある場合のみ）
  タイトル / カード5枚（assist-cards/<ID>.<ext> の画像と名前） / レンタル1枚
  カード画像と名前はリンクにしない
  編成が無い場合はセクション自体を出力しない

同じ血統のモンスター
  ★同一血統内で、自分のIDに近い前後2体ずつ（最大4体）だけを出す。
  全件を出すと同一血統のページが同じブロックを共有し、
  ボイラープレート比率が上がるため。全個体を詳細ページへリンクする。

関連リンク
  <モン類>のモンスター一覧 / モンスター一覧
```

- `<title>`: `<名前>（<血統>・<モン類>）| LINEモンスターファーム徹底攻略`
- `description`: 解説の冒頭から100字前後を抜き出し、改行を除去して1行にする。
  文の途中で切れないよう、句点があればそこで切る。
- noindex ページには AdSense スクリプトを出力しない。

#### CSS の方針

詳細ページは `style.css` に加えて `monster-detail.css` を読み込む。
`monster-detail.css` は `monsters/monster.html` のインラインCSSから
表示部分だけを抜き出し、`.monster-detail-page` 配下にスコープしたもの。
編集フォーム・コメント欄・管理ボタンのスタイルは含めない。

モン類ページは同様に `monster-type.css` を使う。
どちらも既存ページには影響しない（スコープ済み）。

### 5-3. モン類ページ（血統ハブを兼ねる）

血統ページを作らないため、**このページが血統単位のナビゲーションも担う。**

```
パンくず: トップ > モンスター一覧 > <モン類>

h1: <モン類>のモンスター

■ 運営者による解説（taxonomy.json をそのまま出力）
    <heading>                       ← h2
      <subheading>                  ← h3。null なら出力しない
        <body>                      ← p

■ 血統別モンスター                    ← h2
    <血統名>（<所属数>体）             ← h3。リンクにしない
      所属モンスターをカード表示
        名前 / 画像 / オーラ / 副血統 / 限定ラベル
        すべての個体を詳細ページへリンクする
        リンク先の詳細ページがインデックス対象の場合のみ、
        解説の冒頭を抜粋してカード内に表示する
          （独立した「解説つきモンスター」セクションは作らない。
            同じモンスターが1ページに2回並ぶのを避けるため）

■ 他のモン類                         ← h2
    生成済みの他5件へのリンク。生成されていないモン類は出力しない
```

- `<title>`: `<モン類>のモンスター一覧（<所属数>体・<血統数>血統）| LINEモンスターファーム徹底攻略`
- `description`: `sections[0].items[0].body` の冒頭100字前後。句点で切る
- 出力先: `monsters/<monSlug>/index.html`

**血統グループの並び順は所属体数の降順、同数ならID昇順。** 決定的にすること。
**抜粋つきカードは各血統グループの先頭に置き、その中はID昇順。**

抜粋（`mon-type-card-excerpt`）は、**リンク先の詳細ページがインデックス対象の場合のみ**
表示する。解説の有無ではない。

理由：解説が薄いモンスターが大きく表示されると、どのモンスターの解説が
不足しているのかがページ上で判別できなくなるため。表示の大小を
インデックス対象と一致させ、運営者が不足を認識できる状態を保つ。

抜粋を出さないカードはコンパクト表示にする。**リンクは全件に付ける**
（全モンスターに詳細ページがあるため）。

参考として、現時点で見込まれるページ規模を示す。

| モン類 | slug | 所属 | 血統 | インデックス対象 | 解説字数 |
|---|---|---:|---:|---:|---:|
| 創造 | `souzou` | 37 | 5 | 5 | 592 |
| 幻霊 | `genrei` | 62 | 6 | 10 | 604 |
| 魔族 | `mazoku` | 81 | 6 | 11 | 569 |
| 獣族 | `kemono` | 66 | 6 | 14 | 869 |
| 怪物 | `kaibutsu` | 49 | 6 | 7 | 517 |
| 無機 | `muki` | 56 | 5 | 5 | 664 |

解説字数に加えて、モンスターカード（所属数×約20字）と解説抜粋（インデックス対象数×約100字）が
乗るため、いずれも本文量800字ゲートに対して十分な余裕がある。

#### 抜粋・description の切り出し（`descriptionFrom()`）

1. 全角空白・改行を半角スペース1つに正規化する
2. 140字以下ならそのまま返す
3. 先頭140字の中の**最後の「。」**で切る（位置が40字未満の場合は採用しない）
4. 該当する句点が無ければ100字で切り、末尾に `…` を付ける

**文の途中でぶつ切りにしないこと。** カード内の抜粋と `meta description` の
両方がこの関数を使う。

### 5-4. sitemap.xml の再生成

- index対象の詳細ページと生成済みモン類ページを追加する
- **手書きの23URLはそのまま維持**する（P3-1で整理済み。P3-5で薄い日記13本を除外）
- noindex の詳細ページは含めない

## 8. エラー処理

| 事象 | 挙動 |
|---|---|
| 入力ファイルが無い | 即失敗（終了コード1）。何も出力しない |
| 1章の整合性チェックに失敗 | 即失敗。何も出力しない |
| `taxonomy.json` が無い | **詳細ページのみ生成し、モン類ページはスキップ**。警告を出す |
| ゲート条件を満たさない | noindex,follow で生成。sitemap・AdSenseには含めない |
| カードIDが `cards-data.js` に無い | IDをそのまま表示し警告。エラーにしない |
| 画像がGameWithにフォールバック | 警告。エラーにしない |
| インデックス対象HTMLの本文量が800字未満 | **即失敗。** ゲートの計算が誤っている証拠 |

最後の項目が重要。**ビルド自身が出力を検算すること。**
本文量の算出は `visibleChars()` で行う（`<script>` `<style>` `<!-- -->` を除去し、
`<body>` 内のタグを除いた文字列から空白を除去して数える）。

## 12. 静的アシストカード詳細（P12-7 / P12-7b）

### 12-1. 入力と入口

`scripts/build-assist-pages.js`は次の3DBだけを入力とし、表示名による再照合や旧DBの参照をしない。

- `src/data/assist-cards.json`
- `src/data/assist-effects.json`
- `src/data/assist-abilities.json`

`build.js`からモジュールを`require`して呼び、CMS公開Workflowの既存入口へ含める。
単体では`node scripts/build-assist-pages.js`、dry runは`--dry`で実行できる。
追加パッケージ、ビルド時刻、乱数、ファイル列挙順に依存する値は使わない。

### 12-2. 出力とインデックス制御

`assist-cards.json`の入力順で、全カードを`cards/<cardId>.html`へ生成してコミットする。
canonicalは`https://line-monster-farm-tetteikouryaku.com/cards/<cardId>.html`とする。
各ページにカード固有のtitle、description、canonical、h1を出力する。

P12-7b以降は12-4のゲートをHTMLへ適用する。

- 通過: robotsメタを出力せず、sitemapへ掲載し、モンスター詳細と同じAdSenseタグを出力する
- 非通過: `<meta name="robots" content="noindex,follow">`を出力し、sitemap非掲載・広告なしとする
- `assist.html`のマーカー内は3DBから生成し、全カードを`cards/<cardId>.html`へ向ける
- 既存カードの順序は維持し、3DBへ追加されたカードだけを3DB入力順で末尾へ追加する
- 一覧のカード名・レアリティ・画像は3DBを正とし、既存カードもビルド時に同期する
- `cards/card.html`は互換入口として削除しない
- `cards/SSR-hori.html`は`cards/f9-SSR-hori.html`へのcanonical、meta refresh、通常リンクを持つ
  転送ページとし、noindexを付けずsitemapから除外する

2026-08-24の実測はindex 54件、noindex 37件、生成合計91件である。件数は固定値ではなく、
CMS公開後の3DB件数へ動的に追従する。

### 12-3. ページ構成

1. パンくず（トップ > アシストカード > カード名）
2. h1、画像、基本属性（レアリティ、オーラ、カードタイプ、アクセサリー、モン類、イベント2、実装日）。旧距離・地形適性は`event2`へ統合する
3. 管理者による評価。値が無ければ節ごと出さない
4. ステータス。`stats`は`label/value`の3項目、値は`+実数`または`+数値%`。未入力カードは空配列とし、空なら節ごと出さない
5. アシスト効果。`unlockRank`を無凸、1凸、2凸、3凸、4凸の順にグループ化する
6. 能力。`linkStatus: resolved`だけを`sortOrder`順に出す
7. 管理者による解説。空なら節ごと出さない
8. おすすめ編成。無ければ節ごと出さない
9. `assist.html`への導線

`limitBreak`は効果DBと内容が重複するため独立節として出力しない。能力の`ambiguous`と
`unlinked`も出力しない。編成中のカード名はカードDBの`cardId`参照から解決する。

表示は既存の本番カード詳細とサイト共通のサイズ感へそろえる。カード画像は中央配置し、
評価は本番と同じ意味・計算で`/ 5.0`付きのスコアカードへ表示する。入力4項目の表示名は
`ikusei=総合力育成`、`karyo=火力`、`battle=バトル性能`、`ta=他オーラモン類`とする。
`ta`をタイムアタックと解釈してはならない。総合評価は4項目、一致評価は`ta`を除く3項目の
平均を小数第1位で切り捨てる。能力は1件ずつ枠線・影・角丸のあるカードへ分け、能力名、説明、
入手元、タグを同じ枠内に収める。h1・h2・h3はブラウザ既定の見出しサイズと余白へ依存させない。
すべての最上位セクションは共通の
`.section`を使い、解説と後続セクションの間にも通常の余白を確保する。

カードの`accessoryStatus`は`unknown/yes/no`の3状態とする。`unknown`はCMS入力完了まで未確認で、
詳細ページには表示しない。`yes`は「○」、`no`は「なし」と表示する。ルリ
`b17h-MR-ruri`の`cardType`は「アキュメン」を正とする。
カードDBは文章量ゲートと解説量で公開制御するため、カード単位の`status`を持たない。

すべてのDB値をHTMLエスケープする。効果・能力の`description`に含まれる`<br>`だけは
改行として許可し、それ以外のタグは文字列としてエスケープする。サイト共通部分は`style.css`、
生成カード詳細だけの表・評価・能力・見出し階層は`assist-detail.css`へスコープして定義する。
既存ページへ影響する`style.css`の変更は行わない。

### 12-4. インデックスゲート

HTMLのrobots、広告、sitemapへ同じ判定を適用し、標準出力にも結果を報告する。

```text
可視本文 = 効果（name + description）
         + resolved能力（name + description）
         + 解説
```

各文字列は`/<[^>]+>/g`でタグを除去した後の`String.length`を加算する。
ゲートは「可視本文800字以上かつ解説50字以上」とする。解説50字の条件は、効果・能力だけを
登録したカードが自動昇格することを防ぐ歯止めであり、削除しない。通過件数・cardId一覧、
可視本文の最小・中央値・最大・800字以上の件数を出力する。P12-7bの実測は通過54件、
可視本文最小0・中央値870・最大1,677・800字以上54件である。

### 12-5. 検証と決定性

`scripts/verify.js`は3DBから導いた全パスだけをカード生成物として検査する。
`cards/card.html`と`cards/SSR-hori.html`は対象に含めない。

旧`cards/cards-data.js`の91 IDはfragment URLと距離・地形filterの互換入力として全件を3DBへ
包含させるが、3DB側のCMS追加IDは許可する。新規カードを旧データへ追記するために距離・地形を
推測してはならない。`assist.html`は生成差分の許可対象に含める。

- DBのcardIdと生成ページが1対1である
- title、description、canonical、h1が全件にあり、カードごとに固有である
- canonicalが自己URLを指す
- sitemap非掲載なら`noindex,follow`がある
- noindexページに`adsbygoogle`がない
- カード画像参照が実在する
- sitemap掲載ページがゲートを満たしrobotsメタを持たず、広告を持つ
- `assist.html`のリンクが3DB全件と1対1で静的URLとして実在し、旧fragment形式が0件である
- `cards/SSR-hori.html`の転送仕様とsitemap除外を検査する

`node build.js`を2回実行した後、生成HTML全件と`assist.html`がバイト単位で一致し、2回目の更新が0件で
あることを確認する。モンスター生成物と`monsters.html`は変更しない。
