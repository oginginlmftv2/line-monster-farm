## 0. 目的と絶対条件

Firestore から取り出した **モンスター解説57件** を静的HTMLとして出力し、
クローラーから見える形にする。

### 絶対条件（違反したらビルドを失敗させる）

1. **ゲート条件を満たさないモンスターの詳細ページを生成しない。**
   このサイトは過去に348体分のページを生成して「テンプレート」と判定され、
   AdSense に6回落ちている。薄いページの量産は最も避けるべき失敗。
2. **既存の公開HTMLを上書きしない。** 生成先は本仕様で定めたパスのみ。
3. **出力は決定的であること。** 同じ入力なら常に同じバイト列を出力する。
   出力に現在時刻・乱数・実行順依存の要素を含めない。差分が毎回汚れるため。

現在 GitHub Pages は `main` から配信しているため、コミットしないと公開されない。

```html
<!-- 元データ: src/data/monsters-editorial.json / src/data/monster-ids.json -->
```

## 3. ゲート条件

### 3-1. 詳細ページ（57件）

```
生成する条件:
  explanationLength + formationsTextLength >= 500
```

- `explanationLength` は `monsters-editorial.json` の同名フィールド
- `formationsTextLength` は `formations` を文字列化し、
  記号 `" { } [ ] , :` を除いた文字数（無い場合は0）
- **この計算式を変更しないこと。** 閾値の根拠は `docs/monster-id.md` ではなく本仕様が正

条件を満たさないモンスターは**ページを生成しない**。エラーにはせず、
件数と内訳（ID・名前・合計字数）をビルドログに出力すること。

### 3-2. 血統ページ（34件）

```
生成する条件:
  所属モンスターが5体以上  かつ  導入文が「必要字数」以上ある

必要字数 = max(150, ceil50( 850 - (所属数×20 + 詳細ページ数×100 + 300) ))
           ceil50 は50字単位の切り上げ
```

**★必要字数が血統ごとに違う理由**

血統ページの厚みは「導入文 ＋ 所属一覧 ＋ 詳細ページの解説抜粋」で決まる。
詳細ページが少ない血統ほど抜粋が入らず薄くなるため、導入文で補う必要がある。
一律150字にすると12血統が `verify.js` の800字ゲートを通らない。

実装は上の式で計算すること。参考として、現時点（詳細57件）の算出結果を示す。
**P6-2 の執筆はこの表を目標にする。**

| 必要 | 血統（所属数 / 詳細件数） |
|---:|---|
| 450字 | グジラ(7/0) |
| 400字 | アローヘッド(9/0) ヒノトリ(8/0) ゴースト(4/1) ザン(4/1) |
| 350字 | プラント(12/0) ワーム(12/0) スエゾー(11/0) ニャー(10/0) メタルナー(5/1) |
| 300字 | ゲル(13/0) カワズモー(9/1) シンリュウ(8/1) |
| 250字 | ハム(12/1) ガリ(12/1) ネンドロ(12/1) ケンタウロス(11/1) ヘンガー(10/1) キジン(6/2) イルミネ(6/2) |
| 200字 | ナーガ(14/1) ゴーレム(13/1) ライガー(13/1) ウンディーネ(9/2) ユグドラシル(8/2) |
| 150字 | ピクシー(21/4) モノリス(16/2) ドラゴン(14/2) キュービ(13/3) モッチー(12/2) ディノ(10/10) デュラハン(9/5) ジョーカー(9/3) アーク(6/5) |

血統の執筆量は合計 **8,800字**。モン種6本（各400字）と合わせて **11,200字**。

必要字数を満たさない血統はページを生成せず、
**不足字数を明示してログに出すこと**（例: `ワーム: 導入文180字。350字必要。170字不足`）。

**詳細ページ数が増えれば必要字数は下がる。** 解説を書き足して詳細ページが増えた場合、
次のビルドで自動的に緩和される。表はハードコードせず、必ず式で計算すること。

### 3-4. ゲートで落ちた場合の扱い

**リンク切れを作らないこと。** 生成されなかったページへのリンクは出力しない。

- 詳細ページが無いモンスターは、一覧・血統ページで**リンクなしのカード**として表示する
- 血統ページが無い血統は、モン種ページで**リンクなしの項目**として表示する
- パンくずの親が存在しない場合は、その階層をパンくずから省く

## 4. データの解決ルール

### 4-1. 画像の解決順（既存コードと同一にすること）

```
1. monsters-data.js の localImg があればそれ           → monster/<localImg>
2. monster-images.json に該当IDがあればそれ            → monster/<filename>
3. どちらも無ければ GameWith のURL
   https://img.gamewith.jp/article_tools/monsterfarm-line/gacha/Lmonfar_monster_<gwImg>.png
4. gwImg も無ければ画像なし（<img> を出力しない）
```

この順序は `monsters.html` の既存実装と同じ。変更しないこと。

**詳細ページを生成する57体は、全件が 1 または 2 で解決する**ことを確認済み。
3 に落ちた場合はログに警告を出すこと（想定外のため）。

### 4-2. 編成データの表示

`formations` は次の構造。

```json
[{ "title": "おすすめ編成①", "cards": ["a10j-MR-fureria", ...5枚], "rental": "a24j-MR-vitoniru" }]
```

- カードIDは `cards/cards-data.js` の `cardsData[id].name` で**カード名に変換**して表示する
- `cards` は5枚、`rental` は1枚（レンタル枠として区別して表示）
- `cardsData` に存在しないIDは、**カードIDをそのまま表示し、ログに警告**を出す
- カード画像は表示しない（詳細ページの主役は解説のため）

### 4-3. 解説の整形

`explanation` は改行を含むプレーンテキスト。多くが `・` または `･` で始まる箇条書き。

- 改行で分割し、行頭が `・` または `･` の行が**2行以上連続する場合は `<ul><li>` に変換**する
- それ以外の行は `<p>` にする
- 空行は段落の区切りとして扱う
- **HTMLエスケープを必ず行うこと**（`< > &` を実体参照に）
- 行頭の `・` `･` は `<li>` に変換した際に取り除く
- 全角スペースによるインデント（`　`）は保持する

## 5. ページ構成

### 5-1. 共通要素（全生成ページ）

既存ページと同じヘッダー・ナビ・フッターを使う。`style.css` のクラスのみ使用。

| 要素 | 内容 |
|---|---|
| `<title>` | ページ種別ごとに後述。**全ページでユニーク** |
| `<meta name="description">` | 後述。**全ページでユニーク**、80〜120字 |
| `<link rel="canonical">` | 自己参照の絶対URL |
| パンくず | 後述 |
| AdSenseタグ | 既存ページと同じものを入れる |

**`<meta name="robots">` は入れない**（インデックスさせるため）。

### 5-2. 詳細ページ

```
パンくず: トップ > モンスター一覧 > <モン種> > <血統> > <名前>

h1: <名前>

基本情報（既存の .section-box 相当）
  画像
  モン種 / 主血統 / 副血統 / オーラ / 限定ラベル（あれば）
  各項目からモン種ページ・血統ページへリンク

運営者による解説   ← 本文の主役
  explanation を 4-3 のルールで整形して出力

おすすめ編成（formations がある場合のみ）
  タイトル / カード5枚（名前） / レンタル1枚

同じ血統のモンスター
  ★同一血統内で、自分のIDに近い前後2体ずつ（最大4体）だけを出す。
  全件を出すと同一血統のページが同じブロックを共有し、
  ボイラープレート比率が上がるため。詳細ページがある個体のみリンクする。

関連リンク
  <モン種>のモンスター一覧 / <血統>のモンスター一覧 / モンスター一覧
```

- `<title>`: `<名前>（<血統>・<モン種>）| LINEモンスターファーム徹底攻略`
- `description`: 解説の冒頭から100字前後を抜き出し、改行を除去して1行にする。
  文の途中で切れないよう、句点があればそこで切る。

### 5-3. 血統ページ

```
パンくず: トップ > モンスター一覧 > <モン種> > <血統>

h1: <血統>のモンスター一覧

導入文（taxonomy.json。3-2 の必要字数を満たすもの）

所属モンスター（全件）
  カード表示。名前・画像・オーラ・副血統
  詳細ページがある個体はリンク、無い個体はリンクなし

解説つきモンスターの抜粋
  ★詳細ページを持つ個体について、解説の冒頭100字を引用して並べる。
  これにより血統ページが自動的に厚くなる。
  引用元へのリンクを付ける。
```

- `<title>`: `<血統>のモンスター一覧（<所属数>体）| LINEモンスターファーム徹底攻略`
- `description`: 導入文の冒頭100字前後

### 5-4. モン種ページ

```
パンくず: トップ > モンスター一覧 > <モン種>

h1: <モン種>のモンスター

導入文（taxonomy.json、400字以上）

配下の血統一覧
  血統名 / 所属体数 / 代表モンスター3体の名前
  血統ページがあればリンク

モン種全体のモンスター（全件・カード表示）
```

- `<title>`: `<モン種>のモンスター一覧（<所属数>体・<血統数>血統）| LINEモンスターファーム徹底攻略`

### 5-5. sitemap.xml の再生成

- 生成した97ページを追加する
- **既存の37URLはそのまま維持**する（P3-1で整理済み）
- 生成されなかったページのURLは含めない
- `<lastmod>` は入れない（決定的な出力にするため）
- `<priority>`: 詳細 0.7 / 血統 0.6 / モン種 0.6

## 6. インターフェース

```js
// build.js のエントリポイント
main()

// 想定する内部関数（名前は変えてよいが役割は分けること）
loadInputs()            // 入力を読み、1章の整合性チェックを行う
resolveImage(id)        // 4-1 の解決順
formatExplanation(text) // 4-3 の整形。HTMLエスケープ込み
formationsTextLength(f) // 3-1 の文字数計算
renderDetail(monster)   // 詳細ページのHTML文字列を返す
renderBlood(blood)      // 血統ページ
renderMonType(mon)      // モン種ページ
renderSitemap(pages)    // sitemap.xml
writeIfChanged(path, html)  // 内容が同じならファイルを書かない（差分を汚さない）
```

### 実行方法

```
npm run build            生成（既定）
npm run build -- --dry   生成せずレポートのみ
```

`package.json` の `scripts` に `"build": "node build.js"` を追加する。

### 依存パッケージを追加しないこと

Node 18+ の標準機能のみで実装する。テンプレートエンジンを導入しない。
テンプレートリテラルで組み立てる。

## 8. エラー処理

| 事象 | 挙動 |
|---|---|
| 入力ファイルが無い | 即失敗（終了コード1）。何も出力しない |
| 1章の整合性チェックに失敗 | 即失敗。何も出力しない |
| `taxonomy.json` が無い | **詳細ページのみ生成し、集約ページはスキップ**。警告を出す |
| ゲート条件を満たさない | 生成しない。ログに記録。エラーにしない |
| カードIDが `cards-data.js` に無い | IDをそのまま表示し警告。エラーにしない |
| 画像がGameWithにフォールバック | 警告。エラーにしない |
| 生成したHTMLの可視文字数が800字未満 | **即失敗。** ゲートの計算が誤っている証拠 |

最後の項目が重要。**ビルド自身が出力を検算すること。**
可視文字数の算出は `scripts/verify.js` の `visibleChars()` と同じ方法とする
（`<script>` `<style>` とタグを除去し、空白を正規化して数える）。

## 9. 完了の判定

実装が正しいかは、以下で判定する。

1. `npm run build` が成功する
2. 生成ページ数が **詳細57 / 血統34 / モン種6**（taxonomy.json が揃っている場合）
3. `node scripts/verify.js` が FAIL 0。特に「6. 生成ページの品質」が全PASS
4. **2回連続で実行して、2回目の「更新」が0件**（決定的な出力であることの証明）
5. ビルドログの「リンク先が存在しないリンク」が0件

## 10. 実装順の推奨

一度に全部作らず、この順で作ること。各段階で `npm run build` が通る状態を保つ。

```
1. loadInputs と整合性チェックだけ実装し、ログを出して終了する
2. ゲート判定を実装し、57/36 の内訳がログに出ることを確認する
3. renderDetail を実装し、詳細ページ57件を出力する
4. 8章の可視文字数検算を入れ、全件が800字以上であることを確認する
5. sitemap.xml の再生成を実装する
6. taxonomy.json が用意できてから renderBlood / renderMonType を実装する
```

**段階3が終わった時点で一度報告すること。**
57件の詳細ページが期待どおりかを人間が確認してから、集約ページに進む。
