# ブランチ命名規則

**ブランチ名は進捗管理チャットが提示する。** 開発ツールも所有者も自分で考えない。
提示されたブランチ名をそのまま使うこと。

## 書式

```
<type>/<タスクID>-<slug>
```

```
chore/p1-1-agent-rules
feat/p6-1-monster-detail-pages
content/p6-2-taxonomy-intro
fix/p3-1-robots-sitemap
```

**タスクIDを必ず含めること。** これにより、ブランチを見ただけで
`docs/PROGRESS.md` のどのタスクか、完了条件は何かが一意に determined される。
IDが無いブランチは、レビュー時にどのタスクの成果物か判別できない。

## type

| type | 用途 | 例 |
|---|---|---|
| `feat` | 新機能・新規ページ生成・新しい仕組み | ページ生成、ビルド基盤、CMS |
| `fix` | 不具合・設定ミスの修正 | canonical欠落、robots矛盾 |
| `chore` | 設定・文書・ファイル移動・依存関係 | ルール文書、ID生成、エクスポート |
| `content` | 記事・文章の執筆と編集 | 導入文、日記統合、ランキング記事 |
| `refactor` | 挙動を変えない構造変更 | – |

**`content` を独立させているのは、レビューの観点が違うから。**
コードは動くかどうかで判定するが、文章は読んで判断する必要がある。

## slug

- 英小文字とハイフンのみ
- 3語以内、20文字以内が目安
- 日本語・スペース・アンダースコア・大文字を使わない
- 何をするブランチかが分かる語を選ぶ（`update` `fix2` のような無情報な語を使わない）

## 粒度

**原則として1タスク1ブランチ。**

差し戻し（`revert`）が制約違反への基本対応なので、ブランチは小さいほど安全。
大きいブランチは、一部だけ問題があっても全部巻き戻すことになる。

同一フェーズの密結合なタスクをまとめる場合は、タスクIDの代わりにフェーズIDを使う。

```
chore/p3-seo-cleanup        P3-1〜P3-4 をまとめる場合
```

まとめてよいのは、**同じ担当・同じ性質・レビュー観点が同じ**タスクのみ。
`Codexの機械修正` と `Claudeの執筆` を同じブランチに入れないこと。

## 予約語（使用禁止）

```
main        本番
gh-pages    将来の配信分離用に予約。現在は未使用。手で触らない
master      未使用だが予約
```

## 差し戻し後の再作業

`revert` した場合は**新しいブランチを切る**。元のブランチを再利用しない。

```
feat/p6-1-monster-detail-pages          差し戻された
feat/p6-1-monster-detail-pages-v2       やり直し
```

追加コミットで直す場合は、元のブランチをそのまま使う。

## ブランチ不要なタスク

所有者の手作業（Firestore設定、Search Console確認、画像マッチング、シート更新）は
ブランチを切らない。`docs/PROGRESS.md` のブランチ欄は `–` とする。

## マージ後

マージしたブランチは削除する。`docs/PROGRESS.md` のブランチ欄には名前を残す
（あとから履歴を辿るため）。

## 検証

`node scripts/verify.js` が、現在のブランチ名がこの規則に合っているかを検査する。
規則外の名前で作業していると WARN が出る。
