### 1-5. IDが解決する既存の問題

現在 `monsters/monster.html?id=347` は**配列インデックス**を使っています。CLAUDE.md に「先頭や途中に追加すると全モンスターのIDがずれる。過去に2回この問題が起きている」とある通り、構造的な事故源です。

血統ベースのIDは配列順に依存しないため、**この事故が原理的に起きなくなります。** 新モンスターをどこに挿入しても、既存のIDもURLも画像ファイル名も一切変わりません。

## 2. ディレクトリ構造（確定）

### 2-1. URL階層

```
monsters.html（ルート直下・既存）        モンスター一覧（348体）※新規生成はしない
  └ /monsters/<モン種>/                 モン種一覧          6ページ
      └ /monsters/<モン種>/<血統>/      血統一覧           34ページ
          └ .../<ID>.html               モンスター詳細      57ページ（ゲート条件を満たすもののみ）
─────────────────
新規生成 計97ページ
```

具体例:

```
/monsters/mazoku/                       魔族 81体 / 6血統
/monsters/mazoku/pixie/                 ピクシー血統 21体
/monsters/mazoku/pixie/0101.html        ピクシー
/monsters/genrei/mocchi/1625.html       カッパマキ
```

**オーラ別は作りません。**（ご指示どおり。木構造から外れるため、階層の綺麗さを優先）

ただしオーラは**一覧ページのフィルタ条件**としては残します。`/monsters/` と各血統ページで、JSによる絞り込みに使えます。ページを作らないだけで、情報としては失いません。

### 2-3. 画像のファイル名

```

img/monster/1625.jpg        カッパマキ
```

現在の `S__107036676.jpg` のような無意味な名前が、**IDと1対1で対応する名前**になります。マッチング作業の成果がそのままファイル名に固定されるので、二度と迷子になりません。

### 2-4. 血統ページを薄くしないための設計

血統34ページを全部作る必要があります（木構造なので、親が欠けると階層が崩れる）。34本の導入文を書くのは負担なので、**血統ページは詳細ページの解説から自動的に厚くなる**構成にします。

```
血統ページの構成
  ├ 導入文（手書き・150字以上）              ← ゲート条件
  ├ 所属モンスター一覧（カード表示・全件）
  └ 解説のある個体の抜粋（各100字程度・自動）  ← ここで自動的に厚くなる
```

ピクシー血統21体のうち解説持ちが5体あれば、抜粋だけで +500字。**手書きは150字で済み、ページとしては700〜1,000字になります。**

## 3. 開発フローへの差し込み

### 3-1. 改訂フロー

```
P0  Firestore保全                      ← 最優先・他より先
     ルール確認 / バックアップ / Search Console 基準値

P1  ★モンスターID整理                  ← 新設・ここに入れる
     1-1  シートの sortOrder をエクスポート            【済】
     1-2  generate-ids.js で monster-ids.json 生成    【済・38体採番】
     1-3  モン種・血統のローマ字を確定（獣=kemono で確定済み）
     1-4  新規38体のIDをシートに書き戻す（シートを正に保つ）

P2  Firestoreエクスポート
     arrayIndex → ID へ変換して data/monsters-editorial.json
     → 解説のある93体を確定

P3  ★画像整理（93体優先）
     3-1  monster-match.html で93体分をマッチング
     3-2  ID名にリネーム → img/monster/<ID>.jpg
     3-3  残り255体は後追い

P4  ビルド基盤
     build.js / テンプレート / ゲート条件 / Actions

P5  ページ生成
     詳細57 → 血統34 → モン種6 → monsters.html刷新 → sitemap

P6  クリーンアップ（P1〜P5と並行可・独立）
     薄い日記の統合 / noindex / canonical / robots整合

P7  カード活用（reroll刷新・まとめ記事）

P8  CMS実装
```

### 3-2. なぜこの順序か

| 判断 | 理由 |
|---|---|
| **ID整理を最初に置く** | 画像名・URL・ページ生成・sitemap のすべてがIDに依存する。後から変えると全部やり直し |
| **Firestoreエクスポートを画像より先** | 解説のある93体が分からないと、どの画像を優先すべきか決まらない |
| **画像整理をページ生成より先** | ご指摘どおり。生成後に画像を差し替えると再ビルドと再確認が発生する |
| **画像は93体だけ先行** | 414枚すべてを待つと、ページ生成に到達するのが数週間遅れる |
| **CMSを最後** | IDが主キーとして確定していれば、CMSの設計はむしろ簡単になる |
| **クリーンアップは並行** | 他のどれとも依存関係がなく、単独でマージできる |

### 3-3. 絶対に守る順序

> **`monsters-data.js` の配列順を変更する前に、必ず P1（ID生成）と P2（Firestoreエクスポート）を終えること。**

Firestoreの解説データは **`docId = String(配列インデックス)`** で保存されています（`monsters/monster.html` の実装）。配列順が変わると、**65,658字の解説が全部別のモンスターに紐づきます。**

`monster-ids.json` は `arrayIndex` を記録しているので、この2つを先に済ませておけば、以降は配列順を自由に変えられます。

## slug命名方針（確定・2026-08-18）

**この節の内容は確定事項です。以後、slugを変更しないこと。**
実装上の正は `generate-ids.js` の `MON_SLUG` / `BLOOD_SLUG` で、この節はその根拠を記録するものです。

### 方針

> カタカナが **日本のプレイヤーにも一目で分かる英単語の音写** である場合のみ英単語を使い、
> それ以外は **ヘボン式ローマ字** にする。

新しい血統が追加されたときも、この基準で判断します。迷う場合はヘボン式を選んでください。

### ★本家シリーズの英語名は使わない

モンスターファーム本家の英語版（Monster Rancher）では、一部の種族が日本語版と
まったく違う名前になっています。

| 日本語 | 本家英語版とされる名称 |
|---|---|
| ライガー | Tiger |
| ディノ | Zuum |
| ハム | Hare |
| ゲル | Jell |
| モノリス | Monol |
| ヒノトリ | Phoenix |

**これらを採用すると、`/monsters/kemono/tiger/` を見た日本のプレイヤーが
「ライガー」だと分かりません。** このサイトの読者は日本語話者なので、
公式英語名との一致より**カタカナからの推測しやすさ**を優先します。

今後「公式の英語名に合わせるべきでは」という提案があっても、この方針を維持してください。

## 暫定：配列インデックス運用（ID体系への移行までの措置）

この運用は、Firestoreの解説データが配列インデックスをキーにしているために
必要な暫定措置です。P2-2（Firestoreエクスポート）が完了し、
データがID基準に移行した時点で不要になります。

### monsters-data.js
- **必ず配列の末尾に追加すること**
- 先頭や途中に追加すると全モンスターのインデックス（id）がずれ、
  monster.html・monster-match・ピックアップリンクなどが全て壊れる
- 過去に2回この問題が起きている

### 新モンスターのインデックス確認方法
- monsters-data.js の `];` 直前の行が末尾要素
- **インデックス = 配列の要素数 - 1**（要素数はファイル内の `name: '` の数を数えることで確認できる）
- 追加後のインデックス = **現在の末尾インデックス + 1**
- 現在の末尾インデックスは CLAUDE.md の「現在のピックアップ状態」テーブルで確認
- ⚠️ ラインナンバーとインデックスは一致しない（コメント行・宣言行があるためずれる）ので必ず要素数で数えること
