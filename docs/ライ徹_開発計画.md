# LINEモンスターファーム徹底攻略 開発計画

最終更新: 2026-08-22

## 1. 目的

現役運営者の独自コンテンツを守りながら、開発知識が少ない管理者でもClaudeへ依頼して、
通常ページの作業ブランチ作成、検証、PR、mainへのマージまで安全に進められる状態を維持する。

モンスターはGAS版ライ徹CMS、その他のページは通常の作業ブランチという管理境界を崩さない。

## 2. 文書の役割

| 文書 | 役割 |
|---|---|
| `AGENTS.md` | 短い恒久ルールと参照先。開発ルールの唯一の正 |
| `CLAUDE.md` | ガチャ、モンスター、カード、日記などのコンテンツ運用手順 |
| この文書 | 全体計画、段階、完了条件、当初計画からの変更 |
| `docs/PROGRESS.md` | 現在地、完了実績、次の作業、段階間の引き継ぎ |
| `docs/admin-development.md` | 管理者がClaudeへ依頼して開発・公開する具体手順 |

同じ手順を複数文書へ複製しない。恒久ルールは`AGENTS.md`、具体操作は参照先へ置く。

## 3. 現在の前提

| 項目 | 現在値 |
|---|---:|
| モンスター | 351体 |

| モン類ページ | 6件 |
| sitemap | 82URL（既存24 + 詳細52 + モン類6） |
| CMS予測ID検算 | PASS 351体 |

件数はCMS公開で増えるため、計画の完了条件に固定値を使わない。最新値は
`src/data/monster-ids.json`、生成HTML、`sitemap.xml`をスクリプトで集計する。

公開構成:

- GitHub Pagesは`main`を直接配信し、main更新は即公開
- 通常ページは作業ブランチからPRでmainへマージ
- モンスターはGASから`cms/publish`へ送り、Workflowが検算・build・verify後にmainへ直接push
- `gh-pages`、Cloudflare Access、Workerを使う旧案は現在の構成ではない

## 4. 現行の段階

### 第1段階 P10-1: 管理者の開発準備と文書同期

状態: **保留（主要整備はmain反映済み。人工的な実機テストは省略）**

目的:

- 管理者がGitHub、Node.js、Claude、対象リポジトリを使えるか確認できる
- 未保存変更の検出、最新main取得、作業ブランチ作成を固定手順にする
- CMSと通常ページの管理境界を明文化する
- build、verify、更新履歴、PR、即公開の注意を1つの手順へまとめる
- 当初計画と現在の実装・進捗の食い違いを解消する

完了条件:

- `docs/admin-development.md`に環境確認からマージ後確認までがある
- `AGENTS.md`が唯一の正、`CLAUDE.md`がコンテンツ運用という役割が一致する
- 日記のindex対象追加時だけ`existingBlocks.length !== 24`を更新すると明記される
- CMS公開がmainへ直接pushする間は、迂回確認なしにブランチ保護を有効化しないと明記される
- 公開HTML、CMS管理データ、自動生成物を変更せず、`node scripts/verify.js`がFAIL 0

保留理由:

- ルール、管理境界、検証、PR、マージの手順は整備済み
- P10-1のPR作成、Actions確認、mainマージ、リモートブランチ削除まで実際に成功した
- 文書1行だけの人工的なP10-2通し稽古は、実際の更新が無いと価値が小さい
- 残る確認は、第2段階の実際の更新時に同じ手順で行う

再開条件:

- Git・Node.js・Claude・GitHub権限に実際の問題が出た場合
- 通常ページ更新の開始手順やPR操作で管理者が迷った場合
- 公開経路やCMS管理境界が変わった場合

### 第2段階 P11: 実際の通常ページ改善

状態: **次の作業**

目的:

次に必要なカード、日記、トップ、通常記事のうち、実際に必要な1件を選び、
整備済みの安全手順で更新・公開する。ブランチ名は更新内容とタスクIDが決まってから提示する。

完了条件:

- `CLAUDE.md`の対象別手順に従う
- 公開コンテンツの変更なら`index.html`の更新履歴へ1行追記
- 日記はindex対象かnoindexかを先に決め、既存URL数の定数を必要な場合だけ変更
- buildとverifyが成功し、PR差分と本番影響を管理者が確認
- mainマージ後にPC幅・スマートフォン幅で対象ページを目視確認
- 開始からブランチ削除までに問題が出た場合だけ、第1段階を再開して手順へ反映

### 第3段階 P12: 公開経路の追加防御（必要時のみ）

目的:

mainのブランチ保護やマージと公開の分離を検討する場合に、通常PRとCMS公開の両方を止めずに
導入できる設計を作る。

完了条件:

- 現在のGitHub Rules / Branches設定を読み取りで記録
- CMSが使う正規の迂回主体またはPR経由フローを設計
- 本番mainへ適用する前にテスト用ブランチで成功
- 通常PR、CMS公開、失敗時停止、差し戻しをすべて確認
- 管理者の明示承認後だけ設定を変更

この段階は未着手であり、先回りしてブランチ保護を有効化しない。

### 第4段階: コンテンツ改善と再申請

当初P7とP9を引き継ぐ。カード記事、リセマラ記事、Search Consoleの確認、AdSense再申請は
管理者が優先順位と現状を確認してから個別タスクにする。

完了条件はタスクごとに定義し、検索指標や審査結果を推測で「完了」にしない。

## 7. 変更時の共通完了条件

- 最新mainを取得してから作業ブランチを作る
- 編集前に変更予定ファイルと本番影響を宣言する
- モンスター管理対象はGAS版CMS以外から編集しない
- 公開コンテンツの変更は`index.html`の更新履歴へ追記する
- 必要なbuildを行い、すべての変更でverifyがFAIL 0
- 意図しない公開HTML、CMS管理データ、自動生成物を差分に含めない
- 🔴と🟡は管理者が反映タイミングを決める
- 完了実績、次の作業、引き継ぎを`docs/PROGRESS.md`へ同期する
